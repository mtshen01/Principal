目标1：项目地图生成（自动扫描代码库）

📋 新功能。用户选择一个项目 → AI 扫描代码库 → 自动生成页面/模块关联。 新增

方案 A：后端生成「页面节点」JSON
数据结构
{ pages: [ { id: 'p1', name: '登录', file: 'src/pages/login.tsx', type: 'entry', functions: [...] }, { id: 'p2', name: '首页', file: 'src/pages/home.tsx', type: 'main', functions: [...] } ], edges: [ { from: 'p1', to: 'p2', label: '登录完成' } ] }
优点
  • 可复用需求地图画布
  • 交互统一
缺点
  • 后端需定义「页面」识别规则
  • 不同框架差异大
方案 B：后端生成「模块节点」JSON
数据结构
{ modules: [ { id: 'm1', name: '认证', path: 'src/features/auth', exports: [...], imports: [...] }, { id: 'm2', name: '用户系统', path: 'src/features/user', exports: [...], imports: [...] } ], edges: [ { from: 'm1', to: 'm2', label: 'depends' } ] }
优点
  • 通用性强（任意代码库）
  • 依赖关系准确
缺点
  • 需新建「模块地图」画布
  • 较抽象
方案 C：两层复合
结构
pages: [页面/入口] ├─ modules: [内部依赖] └─ functions: [关键流程] edges: [页面间跳转] + [模块依赖]
优点
  • 层级清晰
  • 定位精确
缺点
  • 数据结构复杂
  • 前端需适配
💡 我的建议：选方案 B（模块节点 + 通用识别）
原因：(1) 通用性最强，可覆盖任意代码库；(2) 依赖关系由 AST/import 确定，准确度高； (3) 前端可以是新的「模块地图」或改造现有画布。token 成本可以通过「事实包预喂 + 确定性扫描」压低。

  • 🔗 加载 home 依赖的所有模块

  • 🔄 改完后，地图 re-scan 该页面
场景 B：改项目地图模块

  • 🔗 加载 payment 所有源文件 + 依赖
  • 💬 开启对话：「支持微信退款」
  • 🎨 根据 payment/service.ts 增加新接口
  • 🔄 改完后，自动验证没破坏依赖
❓ 核心疑虑：Token 消耗与可行性
你提出的两个担心
❌ Token 消耗太大 现状： gen-map 单次 ~$0.99（200 文件）
新需求： 项目地图会更细，全量更贵
解法：
  • ✓ 事实包预喂（确定性扫盘）→ 省盲探轮次
  • ✓ 按需加载（用户选模块）→ 不全量扫
  • ✓ 增量更新（变化检测）→ 不重复
❌ 无法准确汇总功能块 现状： LLM 单独扫码容易遗漏
新方案： 确定性 + LLM 混合
  • ✓ AST 解析：100% 准确的导出/导入
  • ✓ 路由表：配置驱动的页面定义
  • ✓ LLM 补语义：这个模块是干什么的
可行性评估
✅ 技术可行：
  • 需求地图画布已成熟（现在在用）
  • 只读代理三层防线已验证（project-optimize 在用）
  • 事实包模式已有先例（gen-map → map-facts）
  • 上下文注入范式已有（apidoc 的消息可切片）
⚠️ 架构改进需求：
  • 拆出「通用地图画布内核」（现在和需求地图耦合）
  • 定义「模块识别规则」（per-project 配置或自适应）
  • 实现「上下文切片」（对话中只注入 N 个模块）
  • 增加「地图diff + 增量」能力
💰 成本 estimate：
  • 单项目地图扫描：~$0.5-1.0（看项目大小）
  • 按需模块加载：~$0.05-0.1 per module
  • 增量diff：~$0.02 per scan
