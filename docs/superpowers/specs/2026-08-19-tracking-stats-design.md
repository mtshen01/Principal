# 埋点统计机器人动作 —— 设计文档

- 日期：2026-08-19
- 状态：已实现，待真机验证
- 触发指令：`帮我统计埋点: <自然语言描述>`

---

## 1. 背景与目标

### 要解决的问题

团队成员想看某个功能的埋点数据时，当前只能人工写 SQL 查生产库，或者去后台报表页翻。前者有门槛，后者只有固定几张报表，问不了「宝宝辅食页面最近一个月多少人访问」这种临时问题。

目标是让飞书机器人接受一句自然语言，自动完成「理解需求 → 查生产埋点 → 出 HTML 报告 → 发回聊天」。

### 前置调研结论（重要，推翻了两个初始假设）

调研 `compass-agent` 后端工程后确认两件事，它们大幅简化了本设计：

**结论一：「神策」是自建接收端，不需要调神策 OpenAPI。**

真实架构是：小程序前端的神策 SDK 按神策协议 POST 到 `compass-agent` 的 `/api/statistics/report`，后端原样落库到 MySQL 表 `statistics_data`。工程内**没有安装任何神策 SDK**，也**没有任何调用神策查询 API 的代码**。所有现有报表（流量看板、DAU、设备分布、分享漏斗等）全部是直接 SQL 查这张表 + `JSON_EXTRACT` 解 `properties`。

因此本功能的取数方式就是：**连 MySQL 跑 SQL**。

**结论二：不需要 ssh 跳板，可从本机直连生产只读库。**

`scripts/user_path_analyzer.py:31-37` 中已存在一个生产外网只读账号。已实测验证（2026-08-19）：

```
host: dongying-prod-public.rwlb.rds.aliyuncs.com:3306
db:   compass_prod
user: compass_viewer（只读）

statistics_data 总行数：1,093,484
数据时间跨度：2026-02-16 ~ 2026-08-19 10:17（实时）
```

原计划的「ssh 进 dev 服务器 → 再连线上服务」这一跳因此被完全砍掉。这不只是省代码，更是省掉一整套 ssh 密钥管理、跳板会话保持、连接失败排查的运维负担 —— 机器人这类无人值守场景，最怕的就是这种多跳长链路的偶发失败。

数据实际保留 **184 天**（约半年）。初稿依据 compass-agent 的一句旧注释写成「约 2.5 个月」，被上面这次实测推翻 —— 详见 §6 的保留期说明。

## 2. 关键数据资产

### 2.1 埋点主表 `statistics_data`

定义在 `compass-agent/models/entities/statistics_data_entity.py:41-77`。

| 字段 | 说明 |
|---|---|
| `distinct_id` | 用户标识，用于 UV 去重与内测排除 |
| `event` | 神策系统事件名，如 `$MPClick` `$MPViewScreen` `$MPLaunch` |
| `time` | 毫秒时间戳 |
| `properties` | JSON。业务信息全在这里 |
| `is_deleted` | 软删除标记 |

**必须知道的口径**：绝大多数业务埋点的 `event` 字段统一是 `$MPClick`，真正的业务事件名在 `properties.event_name`，事件参数在 `properties.params`。按 `event` 字段查业务事件会一无所获。

### 2.2 埋点索引：生产库为准，字典作注解（双源合并）

这一节在实现期做过一次重大修正，原设计把 `user_path_mapping.py` 当成埋点全集，实测证明那是错的。

**实测数据（2026-08-19，近 30 天生产库）**：

| 指标 | 数字 |
|---|---|
| 生产库实际出现的 `event_name` | **593** 个 |
| `EVENT_NAME_MAP` 条目 | 677 条 |
| 库里有、字典查不到中文名 | **331 个（占实际的 56%）** |
| 字典有、近 30 天未出现（已下线/历史） | 415 个 |
| 页面：字典 key 与库内 `$url_path` 直接匹配 | **0 / 82** |
| 页面：去掉前导斜杠后匹配 | 37 / 82 |

两个致命结论：

1. **页面维度按字典原样查会 100% 命中不到数据。** 字典 key 是 `pages-agent/xxx/index`，库里是 `/pages-agent/xxx/index`，差一个前导斜杠。这是最坏的失败形态 —— 不报错、不崩溃，安静地返回空表，报告照常生成并写着「该时段无数据」，读者会以为这个页面真的没人访问。
2. **字典漏掉的 331 个事件不是边角料**，而是正在跑的核心功能：`baby_food_paywall_buy_click`、`baby_food_paywall_pay_success`、`allergy_record_confirm_submit`、`ai_record_voice_toggle` 等。问「宝宝辅食付费转化」这类问题会直接查不到。

根因：`user_path_mapping.py` 是一份**人工维护的中文名对照表**，维护滞后于代码，从来不是为了做全集而存在的。

**因此索引改为双源合并**：

| 源 | 提供 | 角色 |
|---|---|---|
| 生产库 `statistics_data`（近 90 天 distinct + 计数） | 有哪些埋点、各触发多少次 | **事实**，决定全集 |
| `compass-agent/constants/user_path_mapping.py` | 这些埋点叫什么中文名 | **注解**，可缺失 |

合并规则：

- 全集以生产库为准；字典独有的条目保留但标记 `live: false`（历史事件，仍可查，只是排序靠后）
- 页面路径统一**去掉前导斜杠**后比对，快照中同时保存库内原始值供 SQL 使用
- 字典没有中文名的条目，`label` 回退为标识名本身 —— 不致命：`baby_food_paywall_pay_success` 这类命名模型完全读得懂
- 每个条目带 `count`（近 90 天触发次数），作为召回排序权重

这带来的额外收益：召回排序从「纯字面匹配强度」升级为「字面强度 + 真实频次」。同样命中「分享」的 20 个候选里，近 30 天触发 5 万次的排在触发 3 次的前面，比单纯字面匹配靠谱得多。

### 2.3 内测用户名单

生产库 `internal_user` 表。脚本运行时直接查，不硬编码 —— 名单会变，硬编码必然过期。

## 3. 整体架构

新建独立插件 `src/plugins/tracking-stats/`。

**为什么独立而不放进 `team-tools`**：与需求/故障收集不是同一类职责，独立插件才能单独启停，也便于后续单独演进。

注册 order **16**，必须小于 `claude-exec` 的 20 —— 否则触发消息会被 claude-exec 全量接管（这是 `team-tools/index.js:3-6` 已记录的既有约束）。

```
飞书消息「帮我统计埋点: 帮我拿最近一个月的宝宝辅食页面的埋点」
   │
   ├─ ① 触发判定（纯函数，零 LLM）—— 无身份门禁，全员可用
   │
   ├─ ② 冷却 60s / 并发 ≤2 检查，被拒则明确回话
   │
   ├─ ③ 即时应答「正在统计…约需 1~2 分钟」（不 await）
   │
   ├─ ④ 阶段 A · 理解（Haiku 45s，实测耗时 13~28s）
   │      → { range, target, keywords, title }
   │
   ├─ ⑤ 召回（纯函数，零 LLM）
   │      索引 1055 条（697 活跃事件 + 101 活跃页面 + 历史）→ ≤30 候选
   │
   ├─ ⑥ 阶段 B · 精选（Haiku 45s）→ 标识硬校验
   │
   ├─ ⑦ 区间收敛；整体超保留期则直接拒答，不查库
   │
   ├─ ⑧ Python 脚本：连生产只读库 → SQL → 内联 SVG 的 HTML
   │
   └─ ⑨ 先发文字摘要，再传 .html 附件（附件失败降级为回告本地路径）
```

实测总耗时约 40~90 秒，主要花在两次 LLM 上（各 13~28s），查库仅 1~7 秒。

### 模块划分

| 文件 | 职责 |
|---|---|
| `src/plugins/tracking-stats/index.js` | 插件装配出口（`{id, features:[{order:16, feature}]}`） |
| `src/plugins/tracking-stats/feature.js` | feature 本体：触发、限流、编排、回消息 |
| `src/plugins/tracking-stats/logic.js` | 纯函数：前缀解析、索引、召回、区间收敛、QuerySpec 校验、摘要文案 |
| `src/plugins/tracking-stats/throttle.js` | 纯函数：冷却与并发判定（状态容器留在 feature） |
| `src/plugins/tracking-stats/dict.js` | 索引快照加载与缓存 |
| `src/plugins/tracking-stats/understand.js` | 阶段 A / B 的 prompt 与 LLM 调用 |
| `src/plugins/tracking-stats/tracking_report.py` | 连库、跑 SQL、生成 HTML（**与插件同目录**：与 Node 侧共享 QuerySpec 契约，必须同版本） |
| `data/event-dict.json` | 埋点索引快照（双源合并产物） |
| `scripts/sync-event-dict.mjs` | 索引同步脚本（手工运维工具，不参与运行时） |
| `src/integrations/lark.js` | 新增 `uploadFile` / `sendFile` / `sendFileByPath` |
| `src/features/llm-classify.js` | 修正 JSON 提取（见 §5 说明） |

**为什么 Python 脚本放插件目录而非 `scripts/`**：`config.scripts.dir` 在生产环境会被 `APP_DATA_DIR` 覆盖，指向可写的应用数据目录 —— 那是给 action-runner 的**用户自配动作脚本**用的。而本脚本与 Node 侧共享 QuerySpec 契约，两边必须同版本；放数据目录意味着改一边忘了另一边，错误表现是「数字不对」而非清晰报错。放插件目录后，它随 `src/` 一起打包，版本天然一致。

## 4. 触发契约

```
^帮我统计埋点\s*[:：]?\s*(正文)
```

规则：

1. **前缀必须在消息开头**。沿用 `src/app/intent-keywords.js` 的既有铁律 —— 历史事故是整篇接口文档被贴进来，全文命中「错误/异常」而误判为故障。
2. **正文为空则追问**，不启动查询。
3. **正文内容不做任何限制**，可以是任意自然语言。例如 `帮我统计埋点: 帮我拿最近一个月的宝宝辅食页面的埋点` 是完全合法的输入。
4. feature 的 `intents: []`，不参与意图路由，只靠 `match` 判定 —— 与 `bug-patrol` 同款。

### 为什么是前缀匹配而非全等匹配

已有的 `\10001` / `\10002` 可信指令用的是全等匹配，最安全。但本功能后面必须跟自然语言，只能用前缀匹配，宽松度天然更高。安全边界因此放在两处：

- 前缀足够长且不像日常用语（「帮我统计埋点」六字连用，日常对话几乎不会出现）
- 叠加速率与并发保护（见下方「权限」小节 —— 身份门禁经用户拍板取消，改由限流兜底）

### 为什么不做语义识别触发

考虑过让意图分类模型判断「这是不是在要埋点数据」，否决。理由：宽泛匹配 + 兜底分类正是上一轮性能事故的成因（见 `feishu-intent-shrink` 记录）；且本功能要连生产库，误触发代价远高于误判一张需求单。

### 权限：全员可用（用户拍板）

**不设身份门禁**，任何人发送触发指令都能用。`permission: 'any'`，`match` 只判前缀。

> 设计过程中曾提议仅限可信提交人（生产经营数据属敏感信息）。用户拍板：埋点统计是常规功能，团队里谁都该能自助查数，不该卡在一个人身上。
>
> 顺带说明：与之相关的「可信提交人」名单本身保持单人（设置页的「我的飞书 open_id」+ owner）。环境变量 `TRUSTED_OPEN_IDS` 已无任何代码读取，文档与注释同步标注废弃 —— 留着一个不生效却被文档承诺的开关，是下一个「配置看起来在工作、实际没有」的坑。

### 但必须有速率与并发保护

去掉身份门禁后，唯一的闸门就没了，而单次统计的代价并不低：两次 LLM 调用 + 至少两条扫描生产库的聚合查询。没有保护的话，一个群里几个人同时问，或者有人连点几次，就能把共享的生产库拖住 —— 这不是权限问题，是运维问题。

| 保护 | 取值 | 理由 |
|---|---|---|
| 单用户冷却 | 60 秒 | 防连点。同一个人一分钟内重复问同一件事没有意义 |
| 全局并发上限 | 2 | 生产库是共享资源，同时跑的重查询必须封顶 |
| 触发拒绝时 | 明确回话 | 「正在处理其它统计请求，请稍候再试」—— 不能静默丢弃，用户会以为机器人死了 |

冷却与并发都是**内存态**（进程重启即清空）。不做持久化：这是防滥用的软保护，不是安全边界，为它引入存储不值当。

### 群聊

沿用既有规则：群聊中必须 @ 机器人才处理。这一条本身就挡掉了大群误触发。

## 5. 意图识别：两阶段推理

### 为什么必须两阶段

单靠关键词召回撑不住不专业的表述。「宝宝辅食」尚可命中（字典 label 就叫「宝宝辅食…」），但用户若说「小孩吃饭那块」「排敏那个功能」，字面召回直接归零。而召回不到的事件，后续模型再聪明也选不出来 —— **召回决定整个功能的精度上限**。

因此先用一次 LLM 把口语转成规范检索词，再召回，再选择。

### 阶段 A · 理解

输入：

- 用户正文
- **当前日期与时刻（北京时区）**
- 字典的**分类目录**（约 30-40 个业务模块中文名，如「宝宝辅食 / 排敏日历 / 会话 / 分享裂变 / 下单」），由同步脚本从事件名前缀聚类生成

输出：

```js
{
  range: { start: '2026-07-21', end: '2026-08-19' },  // 绝对日期
  target: 'page' | 'event' | 'both',
  keywords: ['宝宝辅食', 'baby_food', '辅食'],          // 同义词扩展后的检索词
  title: '宝宝辅食页面访问情况'
}
```

**注入当前日期是硬要求。** 模型不知道今天几号，不给锚点，「最近一个月」会被算成训练数据里的某个月份。这类错误特别隐蔽：日期格式正确、数字也查得出来，就是错的 —— 比直接报错危险得多。

模型：`config.intent.classifyModel`（`claude-haiku-4-5`），**超时 45s**，走 `src/features/llm-classify.js` 的 `runClassifierOnce`。

> 初稿沿用 `intent.js` 的 10s，实测必然超时 —— 那是短分类 prompt，而这里塞了 40 组业务模块目录 + 4 条规则，实测耗时 13~28s。45s 留了约 60% 余量。**不要顺手把 `intent.js` 也改成 45s**：那条路径每条消息都走，拖慢的是全局。

#### 实现期修正：`llm-classify` 只能解析扁平 JSON

端到端冒烟时本阶段稳定失败，日志显示 LLM 调用**成功**（`is_error: false`）却返回 `null`。根因在 `llm-classify.js` 的提取正则：

```js
out.match(/\{[\s\S]*?\}/)   // 非贪婪：从第一个 { 匹配到第一个 }
```

对嵌套 JSON（本阶段的 `range` 就是内嵌对象）只能截出残缺片段，`JSON.parse` 必然抛错。已改为**括号配对扫描**（处理字符串内的大括号与转义引号），并抽成导出的纯函数 `extractFirstJsonObject` 配单测。

这颗雷埋得很深：现有调用方返回的碰巧都是扁平 JSON，所以一直没炸。**顺带查出 `memory-bank` 的偏好提炼一直踩着它** —— 它的输出是 `{"items":[{...}]}`，长期恒为 null，而其测试用假实现绕过了提取逻辑，故从未暴露。

### 召回（纯函数，零成本）

用阶段 A 的 `keywords` 对字典做三路匹配后合并去重：

1. **中文名子串匹配** —— 「分享」命中所有 label 含「分享」的条目
2. **标识名子串匹配** —— 用户直接说 `chat_sse_send` 这种也能命中
3. **同族前缀扩展** —— 命中 `dish_share_wechat` 时，把 `dish_share_*` 一族拉进候选

按匹配强度排序，**事件与页面合计**取前 **30** 条（不是各 30 条）。`target` 决定召回哪张字典（`page` 查 `PAGE_NAME_MAP`，`event` 查 `EVENT_NAME_MAP`，`both` 两张都查）。

### 阶段 B · 精选

输入：用户正文 + ≤30 条候选（标识名 + 中文名）
输出：**仅 `events` 与 `pages` 两个数组**。其余字段由阶段 A 或纯函数填充，详见第 6 节的字段来源表。

模型与超时同阶段 A。

两阶段串联最坏 20 秒。可接受：用户已收到即时应答，且后续还要跑 SQL、生成 HTML，本就是重活。

## 6. QuerySpec：查询计划契约

LLM 的产物不是 SQL，是一份结构化查询计划。**这是整个设计的安全阀** —— 模型只能填这几个字段，永远碰不到 SQL 拼接。

```js
{
  events: [{ name: 'baby_food_intro_page_view', label: '宝宝辅食介绍页浏览' }],  // 可空
  pages:  [{ path: '/pages/baby-food/index', label: '宝宝辅食首页' }],           // 可空
  range:  { start: '2026-07-21', end: '2026-08-19' },
  metrics: ['pv', 'uv'],
  groupBy: 'day',        // 'day' | 'none'
  compare: true,         // 与上一等长周期环比
  title: '宝宝辅食页面访问情况'
}
```

### 各字段的来源

明确划分，避免两个阶段互相覆盖：

| 字段 | 来源 |
|---|---|
| `range` | **阶段 A 产出，阶段 B 不得修改**。时间解析只做一次 |
| `title` | 阶段 A 产出 |
| `events` / `pages` | 阶段 B 从候选中挑选 |
| `metrics` | 固定 `['pv', 'uv']`，不由模型决定 |
| `groupBy` | 纯函数按跨度推导：跨度 > 1 天为 `'day'`，单日为 `'none'` |
| `compare` | 固定 `true`；上一周期数据不足时报告中省略环比 |

`metrics` 与 `groupBy` 刻意不交给模型：这两项没有歧义空间，交出去只会平白多一个出错面。

### 校验规则（`logic.js` 纯函数，可单测）

| 规则 | 处理 |
|---|---|
| `events[].name` 必须在 `EVENT_NAME_MAP` 中真实存在 | 不存在的条目**直接剔除**（模型编造防线） |
| `pages[].path` 必须在 `PAGE_NAME_MAP` 中真实存在 | 同上 |
| 剔除后 `events` 与 `pages` 同时为空 | **不查询**，回「没找到匹配的埋点事件」+ 附召回候选让用户重说 |
| `events` + `pages` 合计超过 20 条 | 截断至 20（防模型把整个分类全选上） |
| `range` 跨度上限 90 天 | 超出自动收敛，报告中注明 |
| `range` 起点早于数据保留期（180 天） | 抬至保留期起点，报告中注明（**脚注不写这个中间态日期** —— 它可能被 90 天上限进一步收窄，写出来会让人以为报告覆盖到那一天） |
| `range` **整体**早于保留期 | 返回 `outOfRetention: true`，**直接拒答，不查库**。见下方说明 |

#### 保留期的实测值（推翻了一处初始假设）

初稿写「保留期约 2.5 个月」，来自 compass-agent 里的一句旧注释。**实测推翻**：生产库 `statistics_data` 实际数据跨度 `2026-02-16 ~ 2026-08-19`，共 184 天。故 `RETENTION_DAYS = 180`（取保守值）。

这个数字必须大于 `MAX_RANGE_DAYS`（90），否则跨度上限永远不可达、成为死代码 —— 初稿的 75 就犯了这个错。代码里有一条断言专门钉住二者的相对大小，因为这类错误不会让任何单个用例变红，只会让一整条分支静默失效。

#### 为什么整体越界要拒答而不是收敛

若只抬 `start` 不管 `end`，用户问「2025 年双十一那几天」会得到 `2026-02-20 ~ 2025-11-11` 这种**倒挂区间**，`days` 为负。它查 SQL 是 0 行且不报错，报告照常生成写着「该时段无数据」—— 用户会以为双十一那几天真没人用产品。

这正是本设计反复在防的失败模式：不报错、看着像有效结论、实际是错的。所以整体越界时保持用户原始请求值并置 `outOfRetention: true`，让调用方原样复述他要的时间段并说明超出保留期。

「剔完为空就不查询」这条很关键：**回一句「没找到相关事件」远比查出一张空表有用** —— 空表会让人误以为「这个功能真的没人用」，而实际上只是事件名没匹配上。

### MVP 范围（明确不做）

只支持「事件/页面 + 时间范围 + PV/UV + 按天趋势 + 环比」。

**不做**：漏斗分析、留存分析、自定义维度下钻、多事件关联、用户分群。

这些需求存在但低频，且每一个都会显著扩大 QuerySpec 的表达空间，进而放大模型出错面。真遇到复杂需求，人工写 SQL 反而更快。

## 7. SQL 口径

全部沿用 `compass-agent` 现有报表的口径，不自创。口径不一致会导致「机器人给的数跟后台报表对不上」，这种信任崩塌一次就很难挽回。

### 事件查询

```sql
SELECT
  DATE(CONVERT_TZ(FROM_UNIXTIME(time/1000), '+00:00', '+08:00')) AS d,
  JSON_UNQUOTE(JSON_EXTRACT(properties, '$.event_name')) AS ev,
  COUNT(*) AS pv,
  COUNT(DISTINCT distinct_id) AS uv
FROM statistics_data
WHERE time BETWEEN :start_ms AND :end_ms
  AND is_deleted = 0
  AND JSON_UNQUOTE(JSON_EXTRACT(properties, '$.event_name')) IN (:ev0, :ev1, ...)
  AND JSON_UNQUOTE(JSON_EXTRACT(properties, '$."$os"')) != 'devtools'
  AND distinct_id NOT IN (:excl0, :excl1, ...)
GROUP BY d, ev
```

### 页面查询

```sql
... WHERE event = '$MPViewScreen'
    AND JSON_UNQUOTE(JSON_EXTRACT(properties, '$."$url_path"')) IN (...)
```

**传入的必须是快照中保存的库内原始路径（带前导斜杠），不是字典 key。** 字典 key 无前导斜杠，直接拿去查会 0 命中且不报错 —— 见 §2.2。快照的 `pages[].path` 字段存的就是库内原始值，`pages[].key` 才是归一化后用于比对的形式。

### 硬性要求

1. **所有值走占位符绑定**。事件名虽已过白名单校验，仍不拼串 —— 双保险。
2. **北京时区分桶**：`SET SESSION time_zone='+08:00'` + 裸 `DATE(FROM_UNIXTIME(time/1000))`。

   ⚠️ **不要用 `CONVERT_TZ(...,'+00:00','+08:00')`**。初稿这么写并注明「与 `user_behavior_service.py` 一致」，实测推翻：生产库 `@@session.time_zone` 本来就是 `+08:00`，`FROM_UNIXTIME` 已是北京时间，再 `CONVERT_TZ` 就是**加两次 8 小时** —— 每天 16:00 之后的数据全被分到次日。总量不受影响（WHERE 卡的是毫秒戳），但趋势图错位、与后台报表对不上，属于「图看着正常、数就是不对」。compass-agent 全部现有报表用的都是裸 `DATE(FROM_UNIXTIME(...))`。

3. **UV 绝不可相加** —— 无论跨事件还是跨天。`COUNT(DISTINCT)` 不是可加量：连用 7 天的人按天相加会被算成 7 个人。初稿的 `aggregate` 犯了这个错，**实测虚高 52%**（4875 vs 精确 3344）。

   正确做法：`groupBy=day` 时，对每个维度**额外跑一次不分桶的 `GROUP BY k` 查询**取精确 UV（实测约 0.9 秒）。跨项总 UV 同理单独查一次精确值（实测 0.81 秒，与其它查询同量纲）。

   > 初稿曾打算用「各项 UV 的最大值」作为下界估计以省一次查询。实测该省略毫无必要，且当所选事件的用户群不重叠时（如「付费墙」+「过敏记录」）下界可能只有真实值的一半。一份要拿去开会的报告，少一个「这个数不准」的星号是有价值的。
3. **排除 devtools**：`$os != 'devtools'`，对应 `statistics_data_repository.py:28` 的 `EXCLUDE_DEVTOOLS`。
4. **排除内测用户**：运行时查 `internal_user` 表取名单。
5. **只读账号** `compass_viewer`，连接层面无写权限。
6. **单次查询 30s 超时**，结果集上限 5 万行。先按 `time` 收敛再解 JSON。

## 8. HTML 报告

### 布局

```
┌────────────────────────────────────────┐
│  宝宝辅食页面访问情况                     │
│  2026-07-21 ~ 2026-08-19 · 30 天         │
├────────────────────────────────────────┤
│  总访问 12,847 次    独立用户 3,201 人     │  ← 大数字卡片
│  较上一周期 ↑12.3%                       │
├────────────────────────────────────────┤
│  [ 每日趋势折线图 ]                       │  ← 内联 SVG
├────────────────────────────────────────┤
│  明细表：中文名 / 标识名 / 次数 / 用户数 / 占比 │
├────────────────────────────────────────┤
│  查询口径：已排除 devtools 与内测用户       │  ← 脚注
│  今日数据截至 10:30，不完整                │
│  生成时间 / 数据范围 / 事件清单             │
└────────────────────────────────────────┘
```

### 设计约束

**样式全部内联，图表用手写 SVG，不引任何 CDN。** 附件是离线文件，引外链会在断网或内网环境下变成一堆空白框；引 ECharts 则让附件膨胀到 1MB 以上。数据量小，折线柱状足够。

**脚注不是装饰，是必需品。** 数据报告最大的风险是拿去开会的人不知道口径，为一个「对不上的数字」争论半天。把排除规则、时间范围、生成时刻写进文件，成本几乎为零。

**包含今天的区间必须标注「今日数据截至 HH:MM，不完整」。** 否则明天再看同一份报告，今天的数字会「莫名其妙变大」，足以让人怀疑整套系统的可靠性。

### 脚本输出约定

沿用 `scripts/get_qrcode.py:92` 的既有约定：**过程日志走 stderr，stdout 只留最终结果**。

stdout 输出单个 JSON：

```json
{
  "htmlPath": "C:/.../埋点统计_宝宝辅食_20260819_1030.html",
  "summary": {
    "title": "宝宝辅食页面访问情况",
    "range": "2026-07-21 ~ 2026-08-19",
    "totalPv": 12847,
    "totalUv": 3201,
    "compareRate": 0.123,
    "top": [{ "label": "宝宝辅食介绍页", "pv": 5210 }]
  }
}
```

失败时 stdout 输出 `{"error": "..."}` 并 `sys.exit(1)`。

调用经 `src/integrations/shell.js` 的 `runScript`（全项目唯一子进程入口），QuerySpec 经**临时文件**传入而非命令行参数 —— 避免长参数与转义问题。

## 9. 送达

### lark.js 新增能力

当前 `src/integrations/lark.js` 只有 `uploadImage` / `sendImage`，**没有任何发送文件的能力**。SDK（`@larksuiteoapi/node-sdk` 1.71.1）本身支持，且与现有图片接口结构同构：

```js
uploadFile(buf, fileName, fileType = 'stream')
  → client.im.v1.file.create({ data: { file_type, file_name, file } })

sendFile(chatId, fileKey)
  → client.im.v1.message.create({ msg_type: 'file', content: JSON.stringify({ file_key }) })
```

注意点：

- 返回值兜底 `r?.file_key || r?.data?.file_key`（code-gen client 会剥外层信封，现有 `uploadImage` 已验证此行为）
- 飞书限制：**文件 ≤ 30MB，不允许空文件**
- 任意扩展名走 `file_type: 'stream'`
- 所有飞书调用必须经 `lark.js`，这是全项目唯一飞书调用入口

### 发送内容

1. `.html` 附件，文件名 `埋点统计_<标题>_<YYYYMMDD_HHmm>.html`
2. 一段文字摘要：标题、时间范围、总次数、独立用户数、环比、Top3 事件

**为什么附件之外还要发摘要**：飞书对 `.html` 不做在线预览，对方需要下载后用浏览器打开。多发一段文字，对方在聊天里就能看到结论，想细看再点附件。成本几乎为零。

## 10. 失败处理

| 失败点 | 回复 |
|---|---|
| 正文为空 | 「要统计什么埋点？例如：帮我统计埋点: 最近7天分享功能的点击」 |
| 请求区间整体超出保留期 | 原样复述用户要的时间段 + 说明最早可查到哪天，**不查库** |
| 阶段 A 超时 / 返回垃圾 | 「没听懂，换个说法试试」 |
| 召回为空 | 「没找到相关埋点」+ 列出可用的业务分类 |
| 阶段 B 校验后为空 | 「没找到匹配的埋点事件」+ 附召回候选 |
| 数据库连接失败 | 「数据库连接失败」+ 错误摘要 |
| 查询超时 | 「查询超时，请缩小时间范围重试」 |
| 结果为空 | **照常生成报告**，明确写「该时段无数据」—— 空结果本身是有效结论 |
| HTML 生成失败 | 「报告生成失败」+ 错误摘要 |
| 文件上传失败 | 降级：发送文字摘要 + 「文件发送失败」 |

**铁律**：异步长任务外层必须有兜底 catch 并回告，绝不静默失败（沿用 `bug-patrol/index.js:212-217` 的双层 catch 范式）。让用户等一个统计结果等到天荒地老却毫无音讯，是最糟的失败模式。

即时应答不 await 但必须挂 `.catch` —— 发送失败不应中断统计流程。

## 11. 字典同步

### 方案：双源 JSON 快照

`scripts/sync-event-dict.mjs` 做两件事：查生产库拿真实全集与频次，解析 `user_path_mapping.py` 拿中文名，合并生成 `data/event-dict.json`：

```json
{
  "syncedAt": "2026-08-19T10:30:00+08:00",
  "sourceCommit": "35022b1f",
  "liveWindowDays": 90,
  "events": [
    { "name": "baby_food_paywall_pay_success", "label": "baby_food_paywall_pay_success", "count": 1820, "live": true, "named": false },
    { "name": "chat_sse_send", "label": "会话发送", "count": 68210, "live": true, "named": true },
    { "name": "old_removed_event", "label": "已下线的旧事件", "count": 0, "live": false, "named": true }
  ],
  "pages": [
    { "path": "/pages/chat/index", "key": "pages/chat/index", "label": "会话页", "count": 52130, "live": true, "named": true }
  ],
  "categories": [{ "prefix": "baby_food", "label": "宝宝辅食", "count": 74 }]
}
```

字段说明：

| 字段 | 含义 |
|---|---|
| `name` / `path` | **查询时实际使用的标识**。页面用库内原始值（带前导斜杠） |
| `key` | 页面归一化形式（去前导斜杠），仅用于与字典比对 |
| `label` | 中文名；字典没有则回退为标识本身 |
| `count` | 近 `liveWindowDays` 天触发次数，召回排序权重 |
| `live` | 该窗口内是否真实出现过 |
| `named` | 是否有人工中文名（供诊断字典维护缺口） |

结构从 `Record<string,string>` 改成数组：条目要携带 `count`/`live`/`named` 三个属性，字符串映射装不下。

`categories` 由事件名前缀聚类自动生成，供阶段 A 使用。

### 为什么快照而不是运行时直查

运行时每次都查一遍 `SELECT DISTINCT event_name` 要全表扫描，成本远高于查具体几个事件的统计。而埋点清单是低频变化的，快照完全够用。

代价是新埋点上线后要手动同步一次。失败模式温和：**新事件查不到**，而不是整个功能挂掉。快照超过 30 天未同步时在日志中告警。

### 为什么不运行时直读 compass-agent 目录

那会让机器人硬依赖「两个仓库位于同一台机器的固定相对位置」，部署一换地方就崩。同理，`data/event-dict.json` 应当入库 —— 若不入库，这个依赖只是从运行时挪到了部署时，方案价值被抵消。

### 为什么不运行时直接读 compass-agent 目录

那会让机器人硬依赖「两个仓库位于同一台机器的固定相对位置」，部署一换地方就崩。

快照的代价是字典更新后需手动同步一次。但事件字典是低频变更，且**同步滞后的后果是「新事件查不到」，而不是「整个功能挂掉」** —— 这个失败模式温和得多，且可通过快照过期告警缓解：超过 30 天未同步时在日志中提示。

## 附录：被否决的方案及理由

| 方案 | 否决理由 |
|---|---|
| 调神策 OpenAPI 取数 | 工程未接神策云，数据本就在自家 MySQL |
| ssh 进 dev 服务器再连线上 | 生产库有外网只读地址且已实测可直连；多跳链路徒增失败点与运维负担 |

| 让 Claude 现场写 SQL | 慢、不可控，存在写出重查询拖垮生产库的真实风险。可作为 MVP 稳定后的第二档兜底，不作为一期方案 |
| 语义识别触发（无固定前缀） | 宽泛匹配是上一轮性能事故的成因；连生产库的操作误触发代价过高 |
| 全等匹配触发（如 `\10001`） | 本功能必须携带自然语言正文，全等不可行 |
| 无头浏览器截长图 | 需引入 puppeteer 依赖；附件 + 文字摘要已能覆盖「聊天内看到结论」的需求 |
| 事件字典运行时直读 compass-agent 目录 | 硬依赖两仓库的机器与路径关系，部署脆弱 |
