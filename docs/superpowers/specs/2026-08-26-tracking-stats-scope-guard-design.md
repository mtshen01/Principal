# 埋点统计 · 能力边界守卫 —— 设计文档

> 状态：**已拍板，实现中**（决策见第 5 节）
> 关联：`2026-08-19-tracking-stats-design.md`（原设计）、2026-08-26 线上事故
> 前置：本文不扩展任何查询能力，只解决「越界需求怎么回话」

---

## 1. 背景：设计定了边界，实现没有兑现

原设计 §6「MVP 范围（明确不做）」写得很清楚：

> 只支持「事件/页面 + 时间范围 + PV/UV + 按天趋势 + 环比」。
> **不做**：漏斗分析、留存分析、自定义维度下钻、多事件关联、用户分群。

这个决策本身没问题（低频需求，每一个都会显著放大模型出错面）。**问题是实现里没有任何机制让这条边界对用户可见** —— 越界的需求不会被识别，会被当成普通关键词召回，照常产出一份 PV/UV 报告。

原设计通篇在防一种失败模式，§6 里写得最直白：

> 这正是本设计反复在防的失败模式：不报错、看着像有效结论、实际是错的。

而当前的越界处理，恰恰就是这个失败模式本身。

### 触发这份文档的实例（2026-08-26）

用户发：

```
帮我统计埋点: 统计从2026年8月1日至今, 所有付费用户的行为轨迹
```

这一句同时命中两条「明确不做」：

| 用户的诉求 | 命中的禁区 |
|---|---|
| 「所有**付费用户**」 | 用户分群 |
| 「**行为轨迹**」 | 多事件关联 / 漏斗 |

那次因为阶段 A 超时（另一个 bug，已修）而侥幸没有产出报告。**若不超时，用户会收到一份标题类似「付费用户行为轨迹统计」的 HTML 报告**，内容却是若干付费相关事件的 PV/UV 汇总 —— 既不是轨迹，也没有按付费人群过滤。

## 2. 能力边界的代码依据

不是推测，是 `tracking_report.py` 的 SQL 实际能力：

| 能力 | 实现 | 结论 |
|---|---|---|
| 计数 | `COUNT(*) AS pv` | 只有总量 |
| 去重人数 | `COUNT(DISTINCT distinct_id) AS uv` | 只有人数，无人群属性 |
| 时间分组 | `GROUP BY` 天 | 无序列、无路径 |
| 唯一的人维度 | `AND distinct_id NOT IN (SELECT uid FROM internal_user ...)` | **仅用于排除内部账号** |

`statistics_data` 这张表按事件行存储，查询按 `event`/`page` + 时间窗聚合。**没有付费标记可 join，没有事件序列可排序**。

QuerySpec 的字段集（原设计 §6）同样封闭：`events` / `pages` / `range` / `metrics` 固定 `['pv','uv']` / `groupBy` / `compare` / `title`。没有任何位置能表达「人群筛选」或「路径」。

**所以这不是"实现没跟上"，而是设计上就不做。本文只让它诚实。**

## 3. 为什么静默降级是最坏选项

越界需求当前会走完整条链路，产出一份报告。三层危害，逐层加重：

1. **数字对不上诉求。** 用户要轨迹，拿到 PV/UV。
2. **报告标题会复述用户的错误措辞。** `title` 由阶段 A 生成，用户说「付费用户行为轨迹」，模型大概率生成「付费用户行为轨迹统计」。
3. **报告会被截图转发。** 原设计做聊天摘要的理由就是「最容易被直接截图转发」。一张标题写着「付费用户行为轨迹」、内容是全体用户事件 PV 的图，转进决策群就是污染源 —— 而且脱离对话上下文后**无法自证是错的**。

第 3 层是真正的风险：错误结论一旦离开对话现场就再也追不回来。

这与原设计对 `outOfRetention` 的处理逻辑完全同构 —— 那里的结论是「**直接拒答，不查库**」，理由是查了只会得到一张写着「该时段无数据」的报告，而那句话会被读成「那阵子真没人用」。

## 4. 设计

### 4.1 判定：阶段 A 增加 `scope` 字段

阶段 A 的输出 JSON 增加一个字段：

```js
{
  "range": { "start": "...", "end": "..." },
  "target": "event" | "page" | "both",
  "keywords": [...],
  "title": "...",
  "scope": {                      // 新增
    "supported": true | false,
    "unsupported": ["用户分群", "多事件关联"]   // supported=false 时给出命中的禁区
  }
}
```

prompt 里明确列出五类禁区与「能做什么」，要求模型自检。

**为什么交给模型而不是关键词表**：原设计 §6 有一条原则 ——「`metrics` 与 `groupBy` 刻意不交给模型：这两项没有歧义空间，交出去只会平白多一个出错面」。而「是否越界」**恰恰有大量歧义空间**：「用户从首页走到支付都经过哪儿」一个越界词都不含，却是彻头彻尾的路径分析。关键词表必然漏，而这正是模型擅长的语义判断。原则不冲突，反而互补。

**纯函数负责把判定映射成文案**（`logic.js`，可单测），与刚落地的 `buildUnderstandFailureReply` 同一模式。

### 4.2 回话：把边界说清楚，且不复述错误措辞

三条硬要求：

1. **声明位置在第一行**，不是报告脚注。脚注会被跳过。
2. **`title` 必须被改写成实际口径**，绝不沿用用户的越界措辞。这是防截图污染的关键一环 —— 报告自己必须能自证它在统计什么。
3. **明确给出下一步**：这类需求人工写 SQL 更快（原设计 §6 的原话），回话应当这么说，而不是让用户换说法反复试。

### 4.3 非目标

- 不扩展 QuerySpec，不加人群筛选/路径分析。
- 不改 SQL 口径。
- 不改前缀触发契约。
- 不动阶段 B 与硬校验。

## 5. 决策（2026-08-26 已拍板）

**决策 1 = 方案 B（降级 + 显式声明）。**
**决策 2 = 只在聊天回话声明，报告附件不加。**

决策 2 选了较轻的一侧，直接抬高了 title 改写的地位：**它成为报告脱离对话后唯一的防线**。
因此实现上把 title 改写从「让模型重写」改成「**纯函数替换成固定安全标题**」——
让防线依赖模型是自相矛盾的，模型正是越界 title 的来源。固定标题损失一点信息量
（具体统计了哪些事件，报告表格里本来就有），换来的是确定性。

越界时 `title` 一律替换为 `SCOPE_SAFE_TITLE`，不做任何拼接：
在「付费用户行为轨迹统计」前面加个前缀，截图出去照样是错的 —— 必须替换，不能追加。

### 决策 1：越界时给不给数据？

| | 方案 A · 硬拒答 | 方案 B · 降级 + 显式声明（倾向） |
|---|---|---|
| 行为 | 不查库，直接说做不到 | 仍出 PV/UV 报告，但第一行声明「你要的 X 做不到，以下是 Y 口径」，并改写 title |
| 与既有设计的一致性 | 与 `outOfRetention` 拒答一致 | 与 `range.notes`「区间被改写必须写出来」一致 |
| 模型误判（假阳性）的代价 | **高** —— 正常需求被拒，功能变得难用 | 低 —— 用户照样拿到数据，只多一句说明 |
| 误读残留风险 | 无 | 有（用户可能忽略声明），靠 title 改写兜底 |

倾向 B：判定由模型做，就必然有假阳性，而 A 的假阳性代价是「好需求被拒答」，比 B 的「多一句说明」重得多。`outOfRetention` 敢硬拒答，是因为它是日期算术、零假阳性 —— 这个前提在这里不成立。

### 决策 2：报告附件要不要一起加声明？

- **只在聊天回话声明**：改动小，但报告一旦被单独转发就失去上下文。
- **报告顶部也加一条醒目声明（倾向）**：`notes` 机制已存在（原设计要求区间调整必须写进报告），复用它，但要放在顶部而非脚注。

倾向后者，理由同 §3 第 3 层：报告必须能脱离对话自证。

## 7. 验证

- 单测：文案、title 改写、`scope` 形状兜底（模型漏字段/给错类型时的默认值）。
- 端到端（各 1 条，需真实额度）：
  - 越界：「统计从 8 月 1 日至今所有付费用户的行为轨迹」→ 应声明边界，title 不含「行为轨迹」
  - 正常：「最近 7 天分享功能的点击」→ 行为与现在完全一致，不受守卫影响（**防假阳性回归**）

## 8. 风险

**假阳性是主要风险**：模型把正常需求判成越界，会让功能变难用。缓解 —— 采用决策 1 的方案 B 时，假阳性只是多一句说明，数据照给；同时把「正常需求不受影响」作为固定回归用例。

`scope` 字段缺失/类型错时**默认 `supported: true`**（按现有行为走），即老实现的行为。让守卫失效的方向是「退回今天的样子」，而不是「把所有需求都拒掉」。
